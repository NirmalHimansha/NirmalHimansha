Automating Windows Fleet Monitoring & Software Auditing with Nagios Core

November 2026 10 min read Nirmal Himansha

Managing an enterprise fleet of over 100 Windows 10 and Windows 11 workstations, factory terminals, and servers requires far more than basic ping checks. When endpoints operate on dynamic DHCP leases and users interact with local software daily, IT administrators need real-time visibility into hardware health, pending Windows updates, and unauthorized software installations—without manual intervention or alert fatigue.

In this walkthrough, I cover the end-to-end architecture and real-world troubleshooting steps used to deploy a centralized Nagios Core 4.5.14 monitoring infrastructure capable of tracking dynamic DHCP hosts and dispatching instant email alerts whenever software is installed or removed.

1. System Architecture Overview

Rather than deploying heavy commercial agents, the stack relies on lightweight, open-source components communicating over NRPE (Nagios Remote Plugin Executor):

Layer Component / Technology Role in Pipeline
Monitoring Server Debian Linux + Nagios Core 4.5.14 Central scheduling, state evaluation, dashboard UI, and Postfix email alerting.
Client Agent NSClient++ (NRPE Listener) Executes local PowerShell audit scripts and resource checks under LOCAL SYSTEM.
Name Resolution Active Directory DNS + systemd-resolved Dynamically resolves DHCP hostnames without hardcoded IP addresses.
Inventory Storage Central SMB Network Share Stores per-host full software inventory CSV exports (%COMPUTERNAME%.csv).

2. Solving DHCP Name Resolution & DNS Lookups

In an environment where every client workstation receives its IP address dynamically via DHCP, hardcoding static IPs in Nagios host definitions breaks the moment a lease renews. Nagios must resolve every host by its NetBIOS/FQDN hostname using internal DNS.

During initial rollout, several workstations reported check_ping: Invalid hostname/address alongside SERVFAIL responses during nslookup tests. Fixing this required alignment on both the Debian server and the Windows endpoints:

  • Linux Search Domain Routing: On the Nagios Debian host, malformed search domains in /etc/systemd/resolved.conf prevented short hostnames from appending the internal Active Directory domain suffix automatically. Cleaning up the Domains= directive and restarting systemd-resolved restored single-label hostname resolution.
  • Client Dynamic DNS Registration: Windows endpoints whose DHCP leases had drifted out of sync with AD DNS required forcing dynamic registration (ipconfig /registerdns) and verifying that "Register this connection's addresses in DNS" was enabled on the active IPv4 network adapter.

3. Automated Software Inventory & Differential Baseline Auditing

Standard NRPE plugins report point-in-time metrics like CPU load or free disk space, but software auditing requires detecting change over time. Furthermore, returning a list of 200+ installed applications directly over NRPE will exceed its default payload buffer limit and truncate the output.

To solve both constraints cleanly, the PowerShell check script splits its execution into three stages:

  1. Registry Enumeration: Queries both 64-bit and 32-bit Windows Uninstall registry paths while filtering out noisy Windows security updates (KB*).
  2. Centralized CSV Export: Writes the complete software inventory (DisplayName, DisplayVersion, Publisher) to a shared SMB folder so IT staff always have an up-to-date audit file per machine.
  3. Local Baseline Diffing: Compares the current software list against a local cached baseline (C:\ProgramData\Nagios\software_baseline.csv). If software was added or removed, it updates the baseline immediately and exits with code 1 (WARNING).
# Query 64-bit and 32-bit registry hives (excluding Windows KB patches)
$regPaths = @(
    "HKLM:\Software\Microsoft\Windows\CurrentVersion\Uninstall\*",
    "HKLM:\Software\Wow6432Node\Microsoft\Windows\CurrentVersion\Uninstall\*"
)

$installedApps = Get-ItemProperty $regPaths -ErrorAction SilentlyContinue | 
    Where-Object { $_.DisplayName -and $_.DisplayName -notmatch "KB[0-9]{6}" } | 
    Select-Object DisplayName, DisplayVersion, Publisher | 
    Sort-Object DisplayName -Unique

if (-not $installedApps) {
    Write-Host "UNKNOWN: No software entries found."
    exit 3
}

# Export complete software inventory to central SMB share
$ComputerName = $env:COMPUTERNAME
$NetworkShare = "\\CPLW11ITDEP26\NagiosCSV"
$exportPath   = Join-Path $NetworkShare "$ComputerName.csv"

$LocalCacheDir = "C:\ProgramData\Nagios"
if (!(Test-Path $LocalCacheDir)) { New-Item -ItemType Directory -Path $LocalCacheDir -Force | Out-Null }
$BaselineFile = "$LocalCacheDir\software_baseline.csv"

try {
    if (!(Test-Path $NetworkShare)) {
        New-Item -ItemType Directory -Force -Path $NetworkShare | Out-Null
    }
    $installedApps | Export-Csv -Path $exportPath -NoTypeInformation -Force
}
catch {
    Write-Host "WARNING: Software inventory gathered, but failed to write to network share: $_ | AppCount=$($installedApps.Count)"
    exit 1
}

$count = $installedApps.Count
$summaryList = ($installedApps | Select-Object -First 10 | ForEach-Object { "$($_.DisplayName)" }) -join ", "

# Compare against local baseline for change detection
if (!(Test-Path $BaselineFile)) {
    $installedApps | Export-Csv -Path $BaselineFile -NoTypeInformation -Force
    Write-Host "OK: Initial baseline created ($count apps saved). Sample: $summaryList | AppCount=$count"
    exit 0
}

$previousApps = Import-Csv -Path $BaselineFile
$prevNames    = $previousApps | Select-Object -ExpandProperty DisplayName
$currNames    = $installedApps | Select-Object -ExpandProperty DisplayName

$added   = Compare-Object $prevNames $currNames | Where-Object { $_.SideIndicator -eq "=>" } | Select-Object -ExpandProperty InputObject
$removed = Compare-Object $prevNames $currNames | Where-Object { $_.SideIndicator -eq "<=" } | Select-Object -ExpandProperty InputObject

if ($added -or $removed) {
    # Overwrite baseline so the alert clears on the next scheduled check
    $installedApps | Export-Csv -Path $BaselineFile -NoTypeInformation -Force

    $diffDetails = @()
    if ($added)   { $diffDetails += "INSTALLED: $($added -join ', ')" }
    if ($removed) { $diffDetails += "REMOVED: $($removed -join ', ')" }

    Write-Host "WARNING: Software change detected! $($diffDetails -join ' | ') | AppCount=$count"
    exit 1
}

Write-Host "OK: Found $count installed applications (No changes). Sample: $summaryList | AppCount=$count"
exit 0

Handling LOCAL SYSTEM Permissions: Because NSClient++ runs scripts under the NT AUTHORITY\SYSTEM context, ensuring the service account has explicit write access to C:\ProgramData\Nagios is critical. If the baseline file cannot be overwritten after a change is detected, Nagios will remain stuck in a permanent WARNING state on every subsequent check cycle instead of auto-recovering to OK.

4. Configuring Nagios Core for Volatile Warning Alerts

A subtle challenge with self-resetting audit checks is how Nagios handles state transitions and warning notifications. Even when CPU, RAM, and Windows Update critical alerts arrive normally via Postfix, WARNING alerts from a custom audit script can be silently suppressed unless three configuration layers align:

  • Container Service Groups: Nagios 4.5.14 requires every referenced group (such as availability-group, system-resources-group, and inventory-audit-group) to be explicitly declared in a define servicegroup block before any service attaches to it.
  • Volatile Service Behavior (is_volatile 1): Because the script updates its baseline immediately upon detecting a change, the service returns to OK on the very next check. Setting is_volatile 1 instructs Nagios to treat every non-OK output as a distinct event and dispatch an alert immediately.
  • Contact-Level Warning Permissions: Even if a service defines notification_options w,u,c,r, the receiving contact in contacts.cfg will drop warning emails if its own service_notification_options is restricted to c,r. Additionally, Nagios enforces plural directive names (service_notification_commands and host_notification_commands) during pre-flight validation.
# Service Group Containers (windows-fleet.cfg)
define servicegroup {
    servicegroup_name   inventory-audit-group
    alias               Software & Hardware Audits & Updates
}

# Volatile Software Audit Service Definition
define service {
    use                     generic-service
    hostgroup_name          servers,factory-terminals,admin-clients
    service_description     Installed Software Inventory
    check_command           check_nrpe!check_software
    is_volatile             1
    notifications_enabled   1
    notification_options    w,u,c,r
    notification_interval   0
    contact_groups          admins
    servicegroups           inventory-audit-group
}
# Contact Definition Allowing Warning Dispatches (contacts.cfg)
define contact {
    contact_name                    nagiosadmin
    use                             generic-contact
    alias                           Nagios Admin
    service_notification_period     24x7
    host_notification_period        24x7
    service_notification_options    w,u,c,r
    host_notification_options       d,u,r
    service_notification_commands   notify-service-by-email
    host_notification_commands      notify-host-by-email
    email                           admin@paradisetoys.lk
}

5. Operational Results & Takeaways

With this pipeline active across the fleet, the IT team gains two complementary layers of visibility without licensing expensive endpoint management suites:

  • Actionable Email Notifications: Whenever a user or installer adds or removes an application, Nagios sends a single email specifying the exact application name (e.g., WARNING: Software change detected! REMOVED: draw.io 32.6.1) and automatically clears the warning on the next cycle.
  • Queryable Central Inventory: Every workstation continuously maintains its own CSV snapshot on the network share, making compliance audits and license counts as simple as opening a folder.
